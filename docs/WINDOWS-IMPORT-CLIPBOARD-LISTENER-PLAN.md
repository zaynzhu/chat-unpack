# ChatUnpack Windows 截图导入 · 剪贴板监听自动入队方案

> 状态：方案已确认（方向 A），暂未实施；实施前先按本文档评审
>
> 前置依赖：截图导入管线已实机验收（[VALIDATION 2.5](VALIDATION.md)）
>
> 目标平台：Windows 11 23H2+、x64；不改 macOS 代码
>
> 文档日期：2026-09-01

## 1. 背景与问题

截图导入功能本身（OCR、跨图拼接、导出）已验证可用，但交互形态操作成本过高：每截一屏都要循环"Alt+A 截图 → 切换到 ChatUnpack → Ctrl+V 粘贴 → 切回微信 → 滚动"。一条 30 屏的记录等于 30 次循环、约 120 步操作、60 次窗口切换。与 macOS"点一次开始汇总、全程自动"的体验差距过大。

痛点不是识别质量，而是"每屏一次手动循环"这个形态。本方案只消除这个循环，不改变输入来源。

## 2. 目标与非目标

### 目标

- 用户在收图模式下只做两件事：在微信中 Alt+A 截图、滚动到下一段。
- 应用后台监听剪贴板，检测到新图片自动入队，无需切窗口、无需手动粘贴。
- 相同图片自动去重（指纹比对），不会重复入队。
- 图片仅在内存中短暂存在，沿用现有导入管线的一切隐私约束。

### 非目标（明确不做）

- 不绕过微信 `WDA_EXCLUDEFROMCAPTURE` 防截屏（捕获路线已被 VALIDATION 2.4 判死，不再尝试）。
- 不枚举、捕获、OCR、滚动微信窗口；不向微信发送任何按键或输入（SendInput 仅限 FixtureHost 调试，本方案完全不涉及）。
- 不做落盘缓存、不做图片历史、不做后台常驻监听。
- 不改 macOS 端任何代码与文档行为。

## 3. 技术设计

### 3.1 剪贴板监听（新增 `Import/ClipboardListener.cs`）

- 使用 Win32 标准机制：`AddClipboardFormatListener(hwnd)` + `HwndSource.AddHook` 处理 `WM_CLIPBOARDUPDATE`；对应 `RemoveClipboardFormatListener` 注销。
- 监听的生命周期严格跟随 UI 状态：**仅当用户在导入页显式点击"开始收图"后开启，点击"完成收图"或离开导入页立即关闭**。应用启动、后台、最小化常驻状态下绝不监听。
- 收到通知后只查询图片类格式（`CF_DIB` / `CF_BITMAP` / `PNG`），提取 `HBITMAP` 转内存 `BitmapSource`；非图片剪贴板内容直接忽略，不读取、不记录文本或文件列表。

### 3.2 入队与去重（扩展 `Import/ImportedImage.cs` 与 AppViewModel）

- 复用 `ImportedImage.FromBitmapSource(displayName, source)` 构造入队对象，天然继承现有 DIB 脏 alpha 修复（送 OCR 前 `ToOcrSoftwareBitmap` 强制 alpha=255）与内存释放策略（识别完成或清除时 Dispose）。
- 入队前计算感知指纹（复用 `Capture/FrameFingerprint.cs` 的帧指纹思路，必要时补充旋转/裁剪不敏感的降采样哈希）：与队列中任一已有项指纹相同则跳过，并在状态栏提示一次"已跳过 N 张重复图"。
- 手动 `Ctrl+V` 与自动监听共用同一条入队路径（`ImportAddFromClipboardCommand` 的内部实现），两种来源统一去重。

### 3.3 状态机与交互（扩展 `AppViewModel`）

现有 `AppState`（含 `Importing`）保持不变，`Importing` 内部增加收图子状态：

| 子状态 | 监听 | 入队 | 识别 |
|--------|:----:|:----:|:----:|
| 导入·普通 | 关 | 仅手动 Ctrl+V/拖拽 | 手动 |
| 导入·收图中 | 开 | 自动 + 手动 | 手动"开始识别"（或阶段 2 自动） |
| 识别中 | 关（自动关闭） | 拒绝 | 进行中 |

交互要点：

- 导入页新增"开始收图 / 完成收图"按钮与常驻提示："在微信中用 Alt+A 截图即可，应用会自动收取；收图期间其他应用复制的图片也会入队，可逐张移除。"
- 缩略图队列、计数、单张移除、清空沿用现有 UI，仅由自动入队驱动追加。
- "完成收图"与"开始识别"可以合并为一个按钮：点击后先关监听再触发 `StartImportRecognitionAsync()`。

### 3.4 隐私与红线自查（对照 AGENTS.md）

- 不读取微信数据库/缓存/进程内存：监听的是系统剪贴板，内容是用户自己截图放入的。
- 不注入/Hook：仅标准剪贴板窗口消息。
- 未经用户主动触发不工作：监听必须由"开始收图"显式开启，退出即销毁。
- 截图禁止落盘/进日志：沿用 ImportedImage 内存生命周期；`ScanDiag` 诊断只记尺寸/行数/计数，不记图像内容。
- 真实数据不进仓库/测试/commit：自动化验收只用合成图。

## 4. 阶段划分与验证

### 阶段 1：监听 + 自动入队 + 去重（最小可用）

1. 新增 `ClipboardListener`（Win32 监听，开关受收图模式门控）。
2. 入队路径统一 + 指纹去重 + 重复提示。
3. 验证：
   - `ChatUnpack.Core.TestRunner` 全量通过（指纹逻辑若可下沉 Core 则补单测；仅 Win32 交互部分不进 Core）。
   - 实机手动检查：开始收图 → 微信内连续 Alt+A 截 3 张（含 1 张故意重复）→ 队列恰好 3 张、重复被跳过 → 完成收图后识别，结果与手动逐张粘贴一致。
   - 红线自查：收图模式关闭后 `GetClipboardFormatListener` 不再收到消息；诊断日志无图像内容。

### 阶段 2：增量识别（可选增强）

- 收图模式激活时每入队一张即自动触发增量识别，结果页实时追加；识别中收到的图排队串行处理。
- 验证：边截边识别 5 张，中途无崩溃、顺序正确、跨图去重正确；完成收图后总结果与一次性识别一致。

### 记录方式

- 验收结果与已知限制记入 [VALIDATION.md](VALIDATION.md) 新小节（2.6 剪贴板监听收图）；本方案文档状态行同步更新。
- 遵循 Windows 实机验收规则：所有构建、运行、验收在真实 Windows 11 x64 完成，macOS 环境不做任何 Windows 构建声明。

## 5. 风险与边界

| 风险 | 说明 | 处置 |
|------|------|------|
| 其他应用复制的图片混入 | 收图模式下剪贴板是全局的 | UI 明示预期；队列支持单张移除/清空 |
| Alt+A 取消（Esc）不产生图 | 用户取消截图属正常操作 | 无图不报错，状态栏无变化 |
| 高 DPI / 多显示器下截图尺寸差异 | 不影响入队，影响拼接重叠率 | 沿用现有 OverlapMatcher 容差，实机验收覆盖 |
| 监听在应用崩溃后残留 | WM_CLIPBOARDUPDATE 依赖窗口存活 | 窗口销毁监听即失效，无系统级残留 |
| RDP/远程桌面剪贴板行为差异 | 远程会话剪贴板转发可能重复触发 | 指纹去重兜底；列入实机验证项 |

## 6. 工作量预估

- 阶段 1：`ClipboardListener` 约 80-120 行 + AppViewModel/命令接线约 60 行 + 指纹复用改造；预计一次实机会话可完成开发与验收。
- 阶段 2：增量识别调度约 40-80 行；可与阶段 1 同会话或独立进行。
